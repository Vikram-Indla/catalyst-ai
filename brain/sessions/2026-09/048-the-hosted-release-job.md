## What changed
- **The login** (`tools/release.login`), only where GitHub's OIDC variables are present (a
  workstation keeps its own login):
  1. `create-cred-config <provider> --service-account=… --credential-source-url=<token URL>&audience=…
     --credential-source-headers=Authorization=Bearer <request token> --credential-source-type=json
     --credential-source-field-name=value --output-file=$RUNNER_TEMP/gcloud-credentials.json`. The
     credential's source is the job's own token endpoint, so no token is fetched or stored by hand.
  2. `gcloud auth login --cred-file=…`
  3. `gcloud auth configure-docker <registry host> --quiet`
  A missing provider or service account refuses with its name. Every printed command masks the
  request token (`<request-token>`).
- **`.github/workflows/release.yml`**: on every push to `main`, one job `release` holding
  `contents: read` and `id-token: write` (the only job that does). The four settings come from the
  repository's variables; nothing is written in the file. Steps: checkout, the pinned uv setup,
  `make release RELEASE_FLAGS=--print`.
- **Its allowlist row** (`tools/rules.py`, `tools/checks/release_job.py`, wired in `ci.py`):
  - the trigger, the one job, the pinned permissions and environment, the two runs in order;
  - `actions/checkout@v4` as the only action;
  - an action added, a release that is not print-only, a written setting or a wider permission is
    refused.
  - Its enforcement row is RULE-006's "CI job equals the gate", which now names `release.yml`, and
    the selftest's `ci` plant includes a bare workflow the release check refuses (4 violations;
    selftest 58/58). Both were added on a later read of this change, before it landed.
- `make release` passes `RELEASE_FLAGS` through.
