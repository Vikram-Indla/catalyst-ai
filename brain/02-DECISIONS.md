# 02 — Decisions

Operational decisions by the lead, with reasons. Append-only; a reversal is a new row naming the
old one. Architectural decisions are ADRs in `docs/03-adr/`; the row here records adoption.

| ID | Date | By | Decision | Why |
| --- | --- | --- | --- | --- |
| D-001 | 2026-09-18 | lead (proposed) | Adopt the constitution: `RULE-000..009`, `ARCH-001..012`, `ADR-001..007`, the ledgers and the invariants registry, in the backend's shape. | One law across the product's repositories; a contributor moves between them without relearning; every rule names its check. |
| D-002 | 2026-09-18 | lead (proposed) | Adopt `ADR-007`: synchronous operations with idempotency keys below the 20-second job line, polled jobs above it, no callbacks — the service never calls the backend. Announced to the backend before adoption. | Keeps dependency direction one way; the backend's own worker is the only poller; no broker in this service. |
| D-003 | 2026-09-18 | lead (proposed) | The first capability is `improve-story`, the golden capability every later one copies; the first provider adapter is the one the previous system was tuned on. | Consumer pressure from the work-items module; the eval baseline exists in the previous behaviour. |
| D-004 | 2026-09-18 | lead (proposed) | Code quality tightened from the sibling service's rule page: file budget 300 logical lines (from 500), statements ≤ 40, returns ≤ 3, nesting ≤ 3, a duplication check, a 90% overall coverage floor with 100/95/90/80 tiers (from a 60% backstop), two global lint ignores (from three), Python 3.12 (from 3.11). | The same bar as the backend; the sibling's numbers were a first step under a migration, not the standard. |
| D-005 | 2026-09-18 | lead (proposed) | `pip-audit` audits the exported lock, not the editable environment; the runtime image applies Debian upgrades; `make image-scan` runs `trivy --ignore-unfixed` on the release candidate. | An editable self-package cannot be audited; a CVE without a fix is not actionable and would block every release. |
| D-006 | 2026-09-18 | lead (proposed) | `make ci` mounts the git common directory into the CI image so a worktree checkout is a repository inside it. | Working sessions run in worktrees; the image must see the same git the hooks and the git-aware checks see. |
| D-007 | 2026-09-18 | lead (proposed) | The first operation is `POST /v1/improve-story`, operationId `improve_story.run`, per `ARCH-004 §2`; a planning note that named another path shape is superseded by the repository's documentation. | One path rule for every capability; the document is the contract the backend generates from. |
| D-008 | 2026-09-18 | lead (proposed) | `improve-story` v1 retires the rewrite modes of the previous `ai-improve-story` only; the previous `ai-improve-comment` is retired by its own capability `improve-comment` later. | A comment polish has its own rules and a reply-suggestion mode; one prompt serving two contracts would be measured by neither set. |
| D-009 | 2026-09-18 | lead (proposed) | v1 ships on authored, provider-shaped fixtures with the limitation stated in the set README, the ledger and the record; the first live recording replaces them and re-states the numbers. | No provider key exists on the build machine; the pipeline, scanners, graders and budgets are proven now, the model is measured when the key arrives. |
| D-010 | 2026-09-18 | lead (proposed) | `generate-children` is one capability with a `target` field (`stories`, `epics`, `children`), retiring the three previous functions, rather than three operations. | One pipeline, one schema, one prompt with per-target sections, one set with per-target tags — the same reasoning as `improve-story`'s `mode`. |
| D-011 | 2026-09-18 | lead (proposed) | A child level is exactly the parent's next in the supplied hierarchy: a request naming another is `ai.input.rejected`, a completion carrying another is `ai.output.invalid`, both with `hierarchy_violation`. | The hierarchy arrives as data; the service never skips a level; two levels down is two calls the backend makes. |
| D-012 | 2026-09-18 | lead (proposed) | The shared runner, door and repair loop live in `platform/pipeline`; capabilities declare their stages through `Stages(...)`. | The second capability made the runner a rule-of-two case the `dupl` check enforces; the package holds no product noun. |
| D-013 | 2026-09-20 | lead (proposed) | Retrieval is one capability package `search` with three operations (`index.upsert`, `index.delete`, `search.run` with `mode`), not two capabilities `similar-items` and `search-items`; the natural-language-to-filter part of the previous `ai-search-issues` is a separate planned `interpret-query`. | The index operations and the search share one corpus, one storage seam, one embedding version and one budget; two packages would carry two descriptors for one thing, and the previous `ai-search-issues` was a filter translator, not a search — different rules, different set. |
| D-014 | 2026-09-20 | lead (proposed) | A pipeline without a generation call (`search`) declares `parse`, `validate`, `retrieve`, `postprocess`; `tools/checks/pipeline` requires the generation trio (`assemble`, `call`, `validate_output`) as a whole once any of them appears. | Retrieval never instructs a model; forcing an empty `call` stage would be a lie the check protects. |
| D-015 | 2026-09-20 | lead (proposed) | Two database roles assumed with `SET ROLE`: `catalyst_ai_app` on every pooled connection, bound by the tenant policy that reads `app.org_id` (set per transaction); `catalyst_ai_maintenance` only inside the jobs, for the cross-organisation listing; RLS forced on every tenant table. The login user must not be a superuser outside the compose file. | Isolation that survives a bug in the application layer (`ADR-006`), proven by a raw connection in the storage suite; the jobs need to see every organisation without a second connection string. |
| D-016 | 2026-09-20 | lead (proposed) | The retrieval eval runs against a real PostgreSQL with `pgvector` (a throwaway container through `testcontainers`, or `CATALYST_AI_EVAL_DATABASE_URL`), never against the in-memory store. | What the eval must measure is the HNSW index under a tenant filter and the fusion (`ADR-006`'s revisit trigger), which only the real index shows. |
| D-017 | 2026-09-20 | lead (proposed) | Embedding versions are `embedding_model` (the concrete id the adapter used) plus `embedding_version` (`d<dimensions>-r<revision>` from the corpus declaration); a search filters on exactly the current pair; a change is `catalyst-ai reembed`, re-embedding document by document through the same upsert path. | Never a mixed ranking; the transition shows fewer rows, never wrong ones; one code path for indexing and re-indexing. |
| D-018 | 2026-09-20 | lead (proposed) | `generate-children` consults the tenant's index in its retrieve stage (mode `similar`, the child level as the kind filter, the supplied sibling keys excluded, `k` 30) and adds the hits' titles to the sibling pool the lexical `nearest` compares against; the response says `index_consulted`. No embedding call when the organisation has nothing indexed. | De-duplication moves onto retrieval behind the same function (the card's line); the comparison stays deterministic and free; the backend knows whether the index took part. |
| D-019 | 2026-09-20 | lead (proposed) | `budgets` runs after `make evals` (`make budgets-check`), not inside `make lint`; the gate's `--skip` takes a list. | From a clean clone no eval run exists at lint time; the check was red on every fresh CI and green locally only because `.evals/` survived on disk (`F-006`). |
| D-020 | 2026-09-21 | lead (proposed) | Participant tokens are a schema rule: `p1`…`p9999`, one per person per thread, chosen and mapped by the backend; a summary naming any other token is `ai.output.unsafe` (`participant_not_in_thread`); a name-like string inside a comment is text, never an author. | `Q-001` (a) made concrete and enforceable at validation and on output; the token shape the card asked to propose. |
| D-021 | 2026-09-21 | lead (proposed) | A translation always names its target (`ai.input.rejected`, `target_language_required`); the previous functions' inference from the source script is a backend default, not a service rule. | Preservation is every other capability's rule; translation is the one operation that changes the language, and it says to what. |
| D-022 | 2026-09-21 | lead (proposed) | `structure_preserved` and `confidence` on a translation come from deterministic signals in `capabilities/translate/quality.py` — the Markdown skeleton, the kept spans (keys, links, code, placeholders), the target script, the length — and the graders share them; the generic text signals live in `platform/language`. | The backend reads them before replacing a Markdown field; one implementation serves the response and the eval; two capabilities may not import each other. |
| D-023 | 2026-09-21 | lead | `ARCH-003 §1` says one *concern* per package, not one operation: `search` with `index.upsert`, `index.delete` and `search.run` is the shape, and the operations share one descriptor, one eval set and one budget. The page is reworded (1.0.1). | The lead's answer to `Q-006`; the page said operation where it meant concern, and the capabilities check already keys everything on the package. |
| D-024 | 2026-09-21 | lead | Summaries stay synchronous inside the 20-second line; no streamed summary in v1. Streaming is the assistant's contract (`ARCH-004 §3` frames) and lands with the assistant, once, when a surface exists to consume it. | Said in the changelog so nobody builds it twice; the summary sizes fit the line with room. |
| D-025 | 2026-09-21 | lead (proposed) | The workflow proposal schema is the service's, built from `ADR-010`'s five words (statuses, transitions, guards, approvals, reason codes) and the previous system's grammar (one initial in `todo`, a terminal in `done`, reachability, no self-loop, reasons on backward, reject and reopen moves): `statuses[] {key, label, category, initial, terminal, sort_order}`, `transitions[] {from_key?, to_key, kind, guards[], requires_approval, reason_code?, rationale}`. The backend's engine has no published field list yet; the shape is announced to it as a proposal and a rename before it consumes the operation is a `CHANGE`, not a break. | The card's stop condition names a missing field; here the engine has no fields at all, so the service defines the shape it needs, validates structure, and leaves names, permissions, approvals and installation to the engine (`ARCH-002 §2`). |
| D-026 | 2026-09-21 | lead (proposed) | A standup or digest is a `summarize` mode, not a capability: the same participant rule, cap, range and cache; `window` cuts the items in stage 1, `counts[]` are echoed field for field and the model states no number the data lacks; the shapes (`standup[]`, `digest[]`) are laid out deterministically from what the request carries. | One concern per package (`D-023`); the previous digest read seven tables and counted — this service has no source of truth to count from, so it never does. |
| D-027 | 2026-09-21 | lead (proposed) | Outputs that become records — release notes, test cases and artefacts, post-mortem facts and factors — carry a `source_id` (or `covers[]` / `evidence[]`) for every entry, checked against the ids the request carried; an entry that cites nothing it was sent is `ai.output.invalid` (`untraceable_entry`), never returned partial; a test case may cite nothing only with `inferred: true`. The rule lives once in `platform/language/records` beside the participant rule. | These outputs are read as facts by release managers, testers and incident commanders; an invented entry is worse than none (the card's `no_invented_entries`). |
| D-028 | 2026-09-21 | lead (proposed) | The release, test and incident contracts are designed from the hubs' words in `ADR-010` and `ARCH-001 §2` and the previous functions' behaviour, and announced to the backend before its hub modules exist: change ids with `status_category`, criterion and case ids, timeline entry ids, people as tokens. A post-mortem is the incident hub's (a timeline), not the previous business-request retrospective. | The card says the contract is announced so the hub modules consume it, not the reverse; the service creates nothing in a hub. |
