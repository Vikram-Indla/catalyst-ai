# 02 — Decisions

Operational decisions by the lead, with reasons. Append-only; a reversal is a new row naming the
old one. Architectural decisions are ADRs in `docs/03-adr/`; the row here records adoption.

| ID | Date | By | Decision | Why |
| --- | --- | --- | --- | --- |
| D-001 | 2026-09-18 | lead (proposed) | Adopt the constitution: `RULE-000..009`, `ARCH-001..012`, `ADR-001..007`, the ledgers and the invariants registry, in the backend's shape. | One law across the product's repositories; a contributor moves between them without relearning; every rule names its check. |
| D-002 | 2026-09-18 | lead (proposed) | Adopt `ADR-007`: synchronous operations with idempotency keys below the 20-second job line, polled jobs above it, no callbacks — the service never calls the backend. Announced to the backend before adoption. | Keeps dependency direction one way; the backend's own worker is the only poller; no broker in this service. |
| D-003 | 2026-09-18 | lead (proposed) | The first capability is `improve-story`, the golden capability every later one copies; the first provider adapter is the one the previous system was tuned on. | Consumer pressure from the work-items module; the eval baseline exists in the previous behaviour. |
| D-004 | 2026-09-18 | lead (proposed) | Code quality tightened from the sibling service's rule page: file budget 300 logical lines (from 500), statements ≤ 40, returns ≤ 3, nesting ≤ 3, a duplication check, a 90% overall coverage floor with 100/95/90/80 tiers (from a 60% backstop), two global lint ignores (from three), Python 3.12 (from 3.11). | The same bar as the backend; the sibling's numbers were a first step under a migration, not the standard. |
| D-005 | 2026-09-18 | lead (proposed) | `pip-audit` audits the exported lock, not the editable environment; the runtime image applies Debian upgrades; `make image-scan` runs `trivy --ignore-unfixed` on the release candidate. | An editable self-package cannot be audited; a CVE without a fix is not actionable and would block every release. |
| D-006 | 2026-09-18 | lead (proposed) | `make ci` mounts the git common directory into the CI image so a worktree checkout is a repository inside it. | Working sessions run in worktrees; the image must see the same git the hooks and the git-aware checks see. |
| D-007 | 2026-09-18 | lead (proposed) | The first operation is `POST /v1/improve-story`, operationId `improve_story.run`, per `ARCH-004 §2`; a planning note that named another path shape is superseded by the repository's documentation. | One path rule for every capability; the document is the contract the backend generates from. |
| D-008 | 2026-09-18 | lead (proposed) | `improve-story` v1 retires the rewrite modes of the previous `ai-improve-story` only; the previous `ai-improve-comment` is retired by its own capability `improve-comment` later. | A comment polish has its own rules and a reply-suggestion mode; one prompt serving two contracts would be measured by neither set. |
| D-009 | 2026-09-18 | lead (proposed) | v1 ships on authored, provider-shaped fixtures with the limitation stated in the set README, the ledger and the record; the first live recording replaces them and re-states the numbers. | No provider key exists on the build machine; the pipeline, scanners, graders and budgets are proven now, the model is measured when the key arrives. |
| D-010 | 2026-09-18 | lead (proposed) | `generate-children` is one capability with a `target` field (`stories`, `epics`, `children`), retiring the three previous functions, rather than three operations. | One pipeline, one schema, one prompt with per-target sections, one set with per-target tags — the same reasoning as `improve-story`'s `mode`. |
| D-011 | 2026-09-18 | lead (proposed) | A child level is exactly the parent's next in the supplied hierarchy: a request naming another is `ai.input.rejected`, a completion carrying another is `ai.output.invalid`, both with `hierarchy_violation`. | The hierarchy arrives as data; the service never skips a level; two levels down is two calls the backend makes. |
| D-012 | 2026-09-18 | lead (proposed) | The shared runner, door and repair loop live in `platform/pipeline`; capabilities declare their stages through `Stages(...)`. | The second capability made the runner a rule-of-two case the `dupl` check enforces; the package holds no product noun. |
