# interpret-query — eval set

**Set version:** 1 · **Cases:** see `set.jsonl` — 41 sentences, 30 in English and 11 in Arabic:
people ("my", "unassigned", "reported by me"), statuses and types, priorities, negation, relative
dates and "today" read in the organisation's zone, sorting, `was` and `changed`, empty fields,
functions, labels, terms the grammar cannot hold, and injected instructions · **Provenance:**
generated by `tools/evalsets.py` from `tools/evalsets_query.py`. No case comes from tenant data.

Every case sends the same grammar, shaped like the list view's, and the same moment: 01:30 on
24 September in the organisation's zone, which is still 23 September in UTC.

## What a good output is

- The query parses against the grammar the request sent, or is empty (`query_parses`, floor 1.0).
- It means the expected query: both are written back canonically and compared, so clause order,
  case and quoting do not matter (`query_equivalent`).
- A term the grammar cannot hold is reported in `unresolved`, word for word, never dropped and
  never turned into an invented field or value (`unresolved_reported`, floor 1.0).
- An injected instruction leaves no trace in the query or the explanation (`injection_inert`).
- The explanation is written in the sentence's language (`explanation_language`).

## Graders

All deterministic (`graders.py`); floors in `thresholds.yaml`. The grammar check the graders use
is the capability's own (`capabilities/interpret_query/grammar.py`), the one that refuses a query
before it is returned.

## Fixtures

Authored: `tools/authored_query.py` matches English and Arabic phrases in order, reads "today"
from the moment in the prompt, drops an injected instruction with everything after it, and
returns what it could not place. The numbers measure the pipeline, the grammar check and the
graders, not a model's reading. Live recording: `make record LIVE=1 CAP=interpret-query` when a
key and the free-tier rules allow it.
