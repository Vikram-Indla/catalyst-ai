# Start here

The documentation is seven folders. Read them in this order the first time; after that, jump to
what a ticket names.

| Folder | What it holds | Changes how |
| --- | --- | --- |
| `01-architecture/` | `ARCH-NNN` — how the service is shaped: the boundary, capabilities and the pipeline, the contract, providers, retrieval, evaluation, budgets, security, observability, layout, dependency direction | Only through an ADR |
| `02-rules/` | `RULE-NNN` — what every line of code, every prompt and every eval set must satisfy. Binding, each rule mapped to a check | Through a `D-NNN` decision by the lead |
| `03-adr/` | `ADR-NNN` — the decisions and their reasons. Append-only; superseded, never edited | New ADR |
| `04-ledgers/` | Registers: capabilities (with the functions of the previous system each retires), errors, config, providers and models, eval sets, invariants; plus the contract changelog | Generated by `make ledgers` where a source exists; the rest by hand in the same change |
| `05-threat-models/` | `THREAT-NNN` — per capability family, against OWASP ASVS 5.0 and the LLM top ten | With the capability, before production |
| `06-runbooks/` | One page per failure domain: provider outage, eval drift, budget exhaustion, index rebuild | With the capability that needs it |
| `07-GLOSSARY.md` | One word per concept; the vocabulary code, docs, contract and the backend share | Through a `D-NNN` |

## The idea in one paragraph

The AI service is a Python process in front of its own PostgreSQL, called by exactly one client —
the Go backend — through one OpenAPI contract. Each capability is a package with a deterministic
pipeline around one sampled model call: parse, validate, retrieve, assemble, call, validate the
output against a schema, post-process. Providers sit behind one port with recorded fixtures, so
the test suite never touches the network. Every capability ships with a versioned prompt, a
versioned eval set with thresholds, and a cost and latency budget — all three run on every change
— so the honest measure of a feature is a number in the session record, never an impression.

## How a decision travels

```
Q-NNN ─ enough information ─▶ ADR-NNN ─ adoption ─▶ D-NNN ─▶ code · prompt · eval set
  (question)                 (Level 2–3)          (recorded)
```

Level 0–1 decisions live in the ticket and the session record. A product question — tone,
language, what a user may see, whose name a summary may print — is never decided in a prompt; it
is a `Q-NNN` until the lead answers.

## How the pieces hold each other

```
                     RULE-000  (the constitution)
                    ┌──────────┴──────────┐
              ARCH-001..012          RULE-001..009
                    └──────────┬──────────┘
                             ADRs
                               │
                ledgers · eval sets · INV registry
                               │
              tests/architecture · tools/checks · evals gate
                               │
                     make verify  =  CI  =  make ci
```

Every layer is kept true by the one below it, and the bottom one runs on every change.
